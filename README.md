# TT3 성장 경제 시뮬레이터

방치형 게임 TT3의 2층 성장 경제가 **"1시간 체크인 최적 / 저빈도 유저 손실 30% 이내"**
설계 목표를 랜덤성(축복 3택1)과 계단 함수(영웅 해금) 하에서도 유지하는지 검증하는
몬테카를로 시뮬레이터입니다. 표준 라이브러리만으로 동작하며, matplotlib이 있으면
그래프를 저장하고 없으면 텍스트로 대체합니다.

```bash
python3 tt3_sim.py                    # 기본 검증 (= 확정안의 지표)
python3 tt3_sim.py --recommended      # 확정안 회귀 검증 (확정 전과 비교)
python3 tt3_sim.py --sweep            # 민감도 분석
```

같은 경제를 직접 조작해 보는 플레이어블 프로토타입이 `game.html`에 있습니다.
브라우저로 열면 되고 의존성은 없습니다 (외부 요청은 웹폰트뿐). 자세한 내용은 §8.

## 1. 모델 구조

| 층 | 자원 | 성격 | 핵심 파라미터 |
|---|---|---|---|
| 1층 | 금화 | 오프라인 누적, 체크인 빈도와 **무관** | `gold_per_hour`, `gold_offline_eff` |
| 2층 | 균열석 | 스택 수거 + 연쇄, 체크인 빈도에 **민감** | `stack_base`, `stack_cap`, `chain_mults` |

**페르소나** (체크인 스케줄, 단위: 시)

| 이름 | 스케줄 | 체크인/일 | 역할 |
|---|---|---|---|
| `A_저빈도` | 8, 23 | 1.8 | 손실 하한 기준 |
| `B_타깃` | 8, 9, 10, 11.33, 12.5, 13.67, 18, 23 | 7.4 | 설계 타깃 |
| `C_헤비` | 8시부터 1시간 간격 16회 | 14.7 | 독주 상한 기준 |
| `D_쇼츠유입` | 8, 12.5, 18, 22.5 | 3.7 | 신규 유입 온보딩 |

**행동 모델** (선택적, 기본 비활성 — 기존 검증 보존)

- `RetentionCurve` — 일별 접속 확률 지수감쇠. 쇼츠 유입 합성 곡선(D1 100% → D7 44% → D30 13%)
- **내생 번아웃** — 일일 보상이 기대를 초과하면 포만도가 쌓여 접속 확률이 지수 감쇠
- **애착 채널** — 진도 축적이 이탈 해저드를 낮추는 반대 방향 채널

## 2. 검증 제약

| 제약 | 허용 구간 | 의미 |
|---|---|---|
| B/A 비율 | 1.60 ~ 1.80 | 미만이면 체크인 동기 부족, 초과하면 라이트층 이탈 |
| C/A 비율 | ≤ 2.20 | 헤비 독주 경고선 — 탐색 1단계에서도 함께 건다 |
| 연쇄 기여(B) | 8 ~ 12% | 연쇄 루프의 경제적 존재감 |
| 2층 비중(B) | 40 ~ 55% | 한쪽 축이 장식으로 전락하지 않을 것 |
| 번아웃 증분(B) | ≤ +10%p | 현행 설계 대비 활성일 손실 증가분 |

**설계 불변식** (기동 시 자동 검사, `validate_config`)

> `chain_window_h ≥ stack_cap × stack_interval_h`

스택 만충 시간보다 연쇄 창이 좁으면 2층은 **분산 체크인**을, 연쇄는 **밀집 체크인**을
요구해 유저가 양쪽을 동시에 만족시킬 수 없습니다. 두 값이 독립 파라미터라
`stack_cap`만 올려도 모순이 조용히 재발하므로 매 기동 시 검사합니다.

**C/A를 탐색 제약에 넣는 이유**: 연쇄 보상은 체크인 횟수에 비례해 쌓이므로 본질적으로
고빈도(C형)에게 몰립니다. B/A만 제약에 걸고 연쇄를 키우면 C/A가 조용히 경고선을
넘습니다 — C안 단독 적용이 실제로 1.96 → 2.39로 이 함정에 빠졌습니다. 그래서
`_balance_metrics`가 C/A를 4번째 지표로 함께 재고, 3D·4D 탐색의 1단계 필터에서
걸러냅니다. 권장안 선정은 경계에 밀착한 후보(시행 수만 바꿔도 넘어가는 값)를 피하려고
`CA_MARGIN`만큼의 여유를 요구합니다.

## 5. 주요 발견

### 5.1 온보딩

- **첫 승급 `tau_h` 단축은 경제적으로 무효**입니다. 모든 지평에서 ON/OFF 차이 ≤0.07%.
  원인은 유물→`s_max` 환류가 `log10` 압축이라 초반 부스트가 흡수되기 때문입니다.
  예외 창을 첫 50회 승급까지 넓혀도 **+0.32%**에 그칩니다.
- 대신 **초반 직접 부스트**(`onboarding_boost_mult`)는 x2.0에 **+11.8%**로 유효합니다.
- 그러나 번아웃을 켜면 **강도 증분의 96.4%가 이탈로 소멸**합니다. 강도를 6배로 올려도
  60일 총 성장은 평탄(변동 3.0%)하고 활성일만 **−31.1%** 감소합니다.
  **온보딩 강도는 '성장'이 아니라 'D7 진도'만 삽니다.**

### 5.2 D7 진도 목표의 타당성

| 모델 | 관측 상관 r | 개입 시 D30 잔존 |
|---|---|---|
| 번아웃 없음 | −0.037 | +0.0% |
| 번아웃 | −0.030 | **−4.4%** |
| 번아웃 + 애착 | **+0.018** | **−2.2%** |

- 관측 상관은 세 모델 모두 `|r| < 0.05`로 **무정보**입니다.
- 애착 모델은 관측 상관이 **양(+)**인데 개입 효과는 **음(−)**으로 **부호가 반대**입니다.
  상관으로 목표를 정당화했다면 정확히 반대 결론에 도달했을 것입니다.
- **정당화 조건**: 진도 3.3배 코호트의 잔존이 신규 대비 **1.72배**(이탈 42% 감소)여야
  'D7 진도↑ → D30 잔존↑'가 성립합니다. 코호트 로그로 검증 가능한 수치입니다.

### 5.3 두 층의 구조적 모순

스택 만충에 `3 × 55분 = 2.75h`가 필요한데 연쇄 창은 `1.5h`입니다. **양립 불가능한 창**입니다.

- D형 최소간격 4.5h > 연쇄 창 1.5h → **연쇄 0회**. 핵심 루프에서 완전히 배제된 채
  온보딩을 마칩니다.
- 체크인을 묶으면 연쇄는 생기지만 스택 손실로 D7 진도가 **84.5% → 71.7%** 하락합니다.
  보상을 키워도(C안) 역전되지 않아 **보상 크기가 아닌 구조의 문제**입니다.
- **연쇄 창 전역 확대는 불가**합니다 — C/A가 **1.97 → 2.96**으로 경고선을 크게 초과합니다.
  따라서 **온보딩 코호트 한정 예외**만이 해법입니다.

### 5.4 번아웃 모델링

- **기준선은 절대값이 아닌 상대(적응형)여야 합니다.** 절대 기준선은 손실률이 보상강도에
  단조 증가(0.2% → 43.1%)해 저보상 조합이 제약을 자동 통과하는 편향을 만듭니다.
  유저 자신의 최근 보상 EMA를 기준으로 삼으면 **완전 스케일 불변**(5.5% 고정)이 됩니다.
- **허용 구간(deadband)이 필요합니다.** 없으면 축복·지터 같은 정상 변동까지 번아웃으로
  오계상되어 설계와 무관한 상수 손실(40%)이 발생합니다.
- 번아웃은 보상 **수준**이 아니라 **변동성**에 반응합니다
  (`chain_scale` 1→20에서 손실 5.5% → 27.5%).
- **민감도는 단일 운영점에서 식별 불가**합니다. 손익분기는 범위 `r* ∈ [2.8, 6.4]`로만
  보고 가능하며, 서로 다른 보상강도 2개 운영점의 A/B 실측이 있어야 확정됩니다.

## 6. 반증된 가설 (기록)

분석 과정에서 세운 가설 중 데이터로 **기각**된 것들입니다. 재시도를 막기 위해 남깁니다.

| 가설 | 결과 | 실제 |
|---|---|---|
| 온보딩 예외 창을 넓히면(①) 효과가 살아난다 | **기각** | N=50에도 +0.32% |
| 완주 단발 보너스가 상시 배율보다 번아웃이 적다 | **기각** | +27.2% vs +12.6%로 **2배 악화**. 조건부 all-or-nothing이라 변동성을 **증폭** |
| 연쇄 목표와 번아웃 안전은 상충하지 않는다 | **기각** | 절대 기준선 + 잘못된 측정 페르소나가 만든 artifact였음 |
| B형에게 `stack_cap`은 사문화된 값이다 | **기각** | 활용률 68%, cap 변화에 −25%~+22% 민감. 활용률 최저는 오히려 C_헤비(49%) |

`stack_cap`에 대한 실제 발견: 상한 상향(3→5)은 A **+21.1%** / B **+22.2%** / C **+6.1%**로
**헤비가 가장 덜 이롭습니다.** 즉 `stack_cap`은 C/A를 억제하는 **헤비 제동 노브**입니다.
확정안에서 C안의 C/A 부작용을 되돌리는 데 이 성질을 활용했습니다.

## 7. 모델의 가정과 한계

아래는 **실측 데이터가 아닌 가정**입니다. 결론을 인용할 때 반드시 함께 언급해야 합니다.

| 항목 | 상태 | 확정 방법 |
|---|---|---|
| 리텐션 곡선 | 업계 벤치마크 기반 **합성** | 실제 코호트 리텐션 |
| 번아웃 민감도 `s` | **미식별** (시나리오 축) | 보상강도 2개 운영점 A/B 테스트 |
| 애착 계수 | **미측정** (임계값만 역산) | 진도별 코호트 잔존율 |
| 번아웃 메커니즘 자체 | 행동 **가설** | 보상 패턴 변경 전후 리텐션 |

**남은 구조적 caveat**: 확정안은 온보딩 코호트의 연쇄 창만 넓히므로, 일반 유저에 대한
`chain_window_h(1.5h) < stack_cap × stack_interval_h(4.58h)` 모순은 **그대로 남습니다**.
기동 시 불변식 경고로 계속 표시됩니다.

## 8. 플레이어블 프로토타입 (`game.html`)

브라우저로 열면 되는 단일 HTML입니다. 의존성은 없고 외부 요청은 웹폰트뿐입니다.
게임은 두 층으로 나뉘며, 시뮬레이터가 검증한 것은 그중 2층입니다.

### 1층 — 전투 (시뮬레이터가 `gold_per_hour` 하나로 추상화한 부분)

타이탄을 때려 골드를 벌고, 골드로 소드 마스터와 영웅을 키우고, 영웅이 자동으로
싸우는 동안 스테이지가 오릅니다. 스테이지마다 일반 몹 9마리 뒤에 **제한시간
30초짜리 보스**가 있고, 못 잡으면 그 스테이지에서 다시 시작합니다.

**공격은 연타가 아니라 타이밍입니다.** 마커가 바 위를 왕복하고, 중앙에서 누르면
판정이 갈립니다.

| 판정 | 구간 | 배율 |
|---|---|---|
| PERFECT | 중앙 ±5% | ×10 |
| GOOD | 중앙 ±15% | ×6 |
| MISS | 그 밖 | ×1 |

마커가 0.8초마다 중앙을 지나므로 Perfect를 계속 맞히면 초당 12.5배 — 사람이 낼 수
있는 연타(초당 5회 남짓)의 2.5배입니다. 빗나가면 1배로 떨어져 막 누르는 쪽이
손해가 됩니다. 타격마다 왕복 주기를 0.70~1.00초 사이에서 흔들어, 고정 간격
매크로가 계속 맞히지 못하게 했습니다 (고정 0.85초로 120초를 돌리면 141번 중
111번이 MISS). 마커는 게임 배속과 무관하게 실제 시간으로 움직입니다 — 배속을
따라가면 사람이 맞힐 수 없는 판정이 됩니다.

| 곡선 | 값 | 이유 |
|---|---|---|
| 적 HP 성장 | `15 × 1.28^(s-1)` | 골드 성장보다 빨라서 **반드시 벽이 생긴다** |
| 골드 성장 | `3 × 1.27^(s-1)` | |
| 영웅 레벨업 비용 | `base × 1.07^lv` | 비용이 지수라 골드를 다 쏟아도 레벨은 log로만 큰다 |
| 영웅 마일스톤 | 10레벨마다 ×1.8 | 위 때문에 DPS가 선형이면 지수 HP를 못 따라간다 — 이 배율이 그 간극을 메운다 |

벽에 막히면 승급합니다. 유물은 tt3_sim의 승급 공식(`2 × 1.02^(stage-50)`)을
그대로 쓰고, 유물 배율 `(1+relics)^0.35`가 탭 데미지와 영웅 DPS 양쪽에 곱해집니다.
1회차 약 126 → 유물이 쌓이며 148 → 176 → 208 스테이지로 늘어납니다.

### 2층 — 균열 (`tt3_sim.py`가 검증한 경제)

`Config`를 그대로 옮겼습니다. 55분 스택 · 스택별 신선도 · 연쇄 창 1.5h ·
일일 상한 5회 · 완주 보너스 **비례 지급**(확정안)까지 동일하고, 수령 경로는
`Player.check_in`과 1:1입니다. 균열석은 각인으로 들어가 전체 피해에 영구 배율을
줍니다 — 체크인할수록 더 멀리 간다는 설계 의도가 그대로 작동합니다.

### 계측 탭 — `?debug=1` 에서만

플레이에는 필요 없는 설계 검증용 화면이라 기본으로는 숨어 있습니다.
`game.html?debug=1`로 열면 탭이 나타나, 성장 단위·2층 비중·연쇄 기여를
시뮬레이터와 같은 정의로 산출하고 목표 구간 이탈을 표시합니다. 여기에 더해
**실측 골드/시간을 모델 가정(130)과 나란히** 보여줍니다 — 1층 추상화가 이
구현에서 성립하는지 보는 자리입니다.

### 게임 쪽 사정으로 더한 것

- **배속**(실시간 / 60× / 600×) — 기본은 실시간입니다. 배속은 보스 제한시간까지
  함께 당기므로 탭 전투는 실시간이 유리하고, 배속은 방치 구간을 건너뛰는 용도입니다.
- **저장과 오프라인 진행** — localStorage. 자리를 비운 동안 영웅이 계속 싸우고
  균열도 맺히지만, 수령이 없으니 연쇄만 끊깁니다(게임시간 72h 상한).
- **축복 선택 중 시간 정지** — 고르는 동안 연쇄 창이 닫히면 불공평합니다.

온보딩 예외(첫 승급 `tau` 단축, 연쇄 창 4.6h)는 `D_쇼츠유입` 코호트 전용이므로
켜지 않습니다. 로드 시 콘솔에서 경제 23항목을 자체 점검하는데, 2층은 `tt3_sim.py`
확정값과의 일치를, 1층은 "벽이 실제로 생기는가"(HP 성장 > 골드 성장, 마일스톤
도약)를, 타이밍은 판정 경계와 "정확한 한 방이 연타보다 이득인가"를 확인합니다.

캐릭터와 이름, 그래픽은 모두 자체 제작입니다.
